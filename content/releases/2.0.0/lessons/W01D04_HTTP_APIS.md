### דוגמה מקומית

דוגמה זו מדגימה את המנגנון בלי לקרוא למודל. העתק אותה לקובץ `lab.py`, הרץ `python3 lab.py`, ואחר כך בצע את מעבדת הכשל. פלט קבוע של הדגמה אינו תשובת AI.

```python
"""A local HTTP lab: two endpoints, rate limit, bad JSON and a missing route."""
import json
from http.server import BaseHTTPRequestHandler, ThreadingHTTPServer
from threading import Thread
from urllib.request import urlopen


class LabHandler(BaseHTTPRequestHandler):
    def do_GET(self):
        routes = {'/customer': {'id': 'C1', 'name': 'Demo customer'},
                  '/product': {'id': 'P1', 'name': 'Demo product'}}
        if self.path in routes:
            status, body = 200, json.dumps(routes[self.path]).encode()
        elif self.path == '/limited':
            status, body = 429, b'{"error":"rate_limited"}'
        elif self.path == '/invalid':
            status, body = 200, b'not-json'
        else:
            status, body = 404, b'{"error":"not_found"}'
        self.send_response(status)
        self.send_header('Content-Type', 'application/json')
        if status == 429:
            self.send_header('Retry-After', '1')
        self.end_headers()
        self.wfile.write(body)

    def log_message(self, *args):
        pass


def fetch(base: str, endpoint: str) -> dict:
    with urlopen(base + endpoint, timeout=2) as response:
        data = json.loads(response.read().decode('utf-8'))
    if not isinstance(data, dict):
        raise ValueError('expected JSON object')
    return {'source': endpoint, 'data': data}


if __name__ == '__main__':
    server = ThreadingHTTPServer(('127.0.0.1', 0), LabHandler)
    worker = Thread(target=server.serve_forever, daemon=True)
    worker.start()
    try:
        base = f'http://127.0.0.1:{server.server_port}'
        print(fetch(base, '/customer'))
        print(fetch(base, '/product'))
    finally:
        server.shutdown()
        server.server_close()
        worker.join()
```

**מבחן קבלה:** קורא אחר יכול לשחזר את הבנייה מהתיעוד ולבדוק את התוצר, בלי לדעת מראש איזו תוצאה רצית לקבל. עלויות וחיבורים לשירותים אינם מופעלים דרך אתר הלמידה.

### שלבי המימוש

הרץ את הדוגמה ובדוק ששתי התוצאות מכילות ערכים שונים בשדה source. השרת משתמש ביציאה פנויה שבוחר המחשב, ונעצר בסוף הניסוי. הוסף נתיב `/order` עם מזהה הזמנה וסכום. החזר את הנתונים באמצעות אותה פונקציה fetch.

בדוק בנפרד `/missing`, `/limited` ו־`/invalid`. עבור כל נתיב כתוב באיזה שלב אירע הכשל: טיפול בתגובת HTTP, פענוח או בדיקת חוזה הנתונים. בדוק את כותרת Retry-After בתגובה המוגבלת; אל תוסיף לולאת retry לפני שהגדרת מספר ניסיונות ותנאי עצירה.

## Concepts

הלקוח שולח בקשה לשרת. השיטה והנתיב מגדירים פעולה, כותרות נושאות מידע נלווה והגוף נושא נתונים. סטטוס HTTP מעיד על טיפול בבקשה; עדיין צריך לבדוק את תוכן התגובה.

יישם את ההסבר על התוצר שלך: סמן מה נקבע מראש בקוד, מה נקרא ממקור ומה נוצר או הוערך על ידי מודל. אלה מסלולים שונים של אחריות. ערך שנוצר אינו נעשה עובדה רק מפני שהוא כתוב בשדה מובנה.

### בקשה ותשובה

כתובת מורכבת מסכמה, מארח, יציאה ונתיב. בדוגמה `http://127.0.0.1:<port>/customer`, השרת רץ במחשב שלך; זו מעבדה מקומית שאינה משתמשת ב־HTTPS או באימות. ב־API עסקי מרוחק נדרשים חוזה השירות, TLS ומנגנון אימות מתאים.

GET קורא משאב. POST משמש לבקשה עם גוף, למשל יצירת רשומה לפי חוזה השירות. 2xx מציין הצלחה ברמת HTTP, 4xx מציין בעיה בבקשה ו־5xx בעיה בצד השרת. 200 עם גוף פגום עדיין נכשל כשמנסים לפענח נתונים. 429 מציין שהשרת הגביל את קצב הבקשות; אין לנסות שוב ללא גבול.

Timeout מגביל כמה זמן הלקוח ממתין. הוא אינו מוכיח שהשרת לא ביצע פעולה. בדוגמה `urlopen` עשוי להעלות `HTTPError` עבור סטטוס שגיאה; `json.loads` מעלה כשל פענוח עבור גוף שאינו JSON. שמור את ההבחנה כדי לאבחן נכון.

## Deep Dive

### ניסוי קטן לפני מערכת גדולה

הפרד שלושה חוזים: קלט המשתמש, החלטת המודל ותוצאת הכלי. למשל, פנייה מכילה טקסט; החלטת המודל מבקשת lookup_product עם מזהה; תוצאת הכלי מכילה מחיר מהקטלוג. אלה אינם אותו אובייקט. בדיקה של JSON אינה מאמתת את המחיר, והצלחת כלי אינה מוכיחה שהמודל סיכם אותו נכון.

לפני חיבור מודל, כתוב תוצאה צפויה למקרה תקין ולמקרה חסר. לקוח בדיקה מחזיר החלטות קבועות ומאפשר לבדוק את הבקר. אחרי חיבור מודל, שמור גם את תשובותיו ובדוק התאמה לציפייה. אל תחליף בין שני סוגי הראיות.

תוצר בסיס טוב כולל README עם הוראות הרצה, תלות בגרסאות, דוגמאות בדיקה ומגבלות. אל תבנה מערכת שלמה כדי ללמוד תנאי אחד; בנה את החלק שהיחידה מבקשת, הסבר אותו והוכח שהוא עובד.

חקור החלטה אחת לעומק: מה היית משנה אם כמות הנתונים גדלה פי עשרה, אם מקור אינו זמין או אם אדם אחר מקבל אחריות על התהליך? כתוב שתי חלופות, הנחה לכל חלופה וניסוי שיכול להכריע ביניהן. מספרים שבחרת לתרגיל הם הנחות, לא הבטחה לתוצאות אצל לקוח.

קרא את המקור המקושר וחפש את המנגנון הנוגע להחלטה שלך. רשום מועד קריאה, גרסת תוכנה והבדלים בין התיעוד לבין מה שהרצת. בתרגיל המבוסס על ספק, בדוק בחשבון שלך את זמינות המודל או התכונה ואת מגבלות מסלול החשבון.

## Failure Lab

**הכשל שיש להזריק:** בדוק 404, 429 וגוף שאינו JSON. הפרד שגיאת תקשורת משגיאת נתונים.

שמור עותק תקין, ואז צור מקרה נכשל אחד. רשום קלט, ציפייה, תוצאה והודעת שגיאה. אתר את הרכיב הראשון שבו התוצאה סטתה מהציפייה; שינוי הפרומפט אינו תיקון אוטומטי לבעיה בהרשאה, ברשת או בנתונים.

תקן את הגורם, הרץ שוב את המקרה הנכשל ובדוק גם את המסלול התקין. הוסף את המקרה לבדיקות הרגרסיה. הצג ראיה שהתיקון עובד, ולא רק הסבר שהוא אמור לעבוד.
