## Mission

איך אפליקציות LLM פועלות: בנה תוצר שאפשר לבדוק והסבר את ההחלטות שמאחוריו. התוצר הוא חלק מתיק העבודה בנושא יסודות ובנייה מאפס.

**מטרת הבנייה:** הרץ אותה משימת סיכום עם מסמך קצר, מסמך ארוך והקשר חסר. שמור את הקלט, הפלט, מספר הטוקנים שנצרכו וזמן התגובה.

תכנן עד 180 דקות. אם חסר לך ידע בסיסי, חזור ליחידה שמוגדרת כדרישת קדם במקום לדלג על הבדיקה. יחידה זו היא חוברת תרגול מעשית עם הסבר תמציתי ומקורות להעמקה. היא אינה מדריך מלא עם פתרון מוכן להעתקה.

## Build First

הרץ אותה משימת סיכום עם מסמך קצר, מסמך ארוך והקשר חסר. שמור את הקלט, הפלט, מספר הטוקנים שנצרכו וזמן התגובה.

1. פתח תיקיית עבודה נפרדת. כתוב ב־README מהו הקלט, מהו הפלט ומי רשאי להפעיל את התהליך.
2. צור דוגמה קטנה בתחום שבחרת: עסק שמקבל פנייה מלקוח. השתמש בשם בדוי ובנתוני בדיקה; אל תחבר לקוח אמיתי בשלב הבנייה.
3. הגדר את התוצאה המצופה לפני ההרצה: רשומה, מסמך, שינוי מצב או פעולה. הפרד בין תוצאה שמודל הציע לבין פעולה שהקוד ביצע.
4. ממש מסלול תקין אחד. אם זו משימת אפיון, מסור תרשים וטבלת החלטות במקום קוד מיותר. אם נדרש ספק חיצוני, בדוק גישה והרשאות בתיעוד המקושר ושמור את גרסת החבילה.
5. שמור קלט, פלט ומזהה הרצה. השווה את התוצאה לציפייה והראה היכן היא תואמת והיכן לא.

**מבחן קבלה:** קורא אחר יכול לשחזר את הבנייה מהתיעוד ולבדוק את התוצר, בלי לדעת מראש איזו תוצאה רצית לקבל. עלויות וחיבורים לשירותים אינם מופעלים דרך אתר הלמידה.

## Concepts

טוקנים הם יחידות הייצוג של המודל, ולא בהכרח מילים. הקשר הוא המידע הנגיש בקריאה הנוכחית. תשובה יכולה להשתנות גם בלי שינוי קוד; אין להסיק אמינות מסגנון בטוח.

יישם את ההסבר על התוצר שלך: סמן מה נקבע מראש בקוד, מה נקרא ממקור ומה נוצר או הוערך על ידי מודל. אלה מסלולים שונים של אחריות. ערך שנוצר אינו נעשה עובדה רק מפני שהוא כתוב בשדה מובנה.

### מה נכנס לקריאה

טוקן הוא יחידת ייצוג שהמודל מעבד; הוא אינו בהכרח מילה אחת. אותו משפט בעברית ובאנגלית עשוי להתחלק אחרת. חלון ההקשר מגביל את הקלט והפלט לפי המודל והממשק. היסטוריה ארוכה אינה זיכרון חיצוני אמין: צריך להחליט מה לשלוח בכל בקשה.

הוראות מגדירות משימה וסגנון; הקשר מספק מידע רלוונטי; דוגמאות מדגימות מבנה. אל תערבב מסמך לא מהימן עם הוראות מערכת. הסבר שהמודל כותב על החלטתו אינו trace של התוכנה ואינו הוכחה שפעולה בוצעה.

מדוד זמן התחלה וסיום, נתוני usage שהשירות מחזיר ותוצאת בדיקה. מחיר מחושב לפי התמחור העדכני של הספק, ולא לפי מספר תווים בלבד. בדוגמת ההשוואה שמור את אותו קלט ושנה משתנה אחד בכל פעם.

## Mental Model

```text
Input → Contract check → Work / model proposal → Result check → Evidence
                                    ↓ failure
                             Stop / review / recover
```

החלף כל תיבה בשם רכיב מהבנייה שלך. אם יש שינוי במערכת חיצונית, הוסף שלב הרשאה לפני הביצוע ושלב אימות אחריו. אם אין פעולה חיצונית, אל תוסיף שלבים שאין להם תפקיד.

## Deep Dive

### ניסוי קטן לפני מערכת גדולה

הפרד שלושה חוזים: קלט המשתמש, החלטת המודל ותוצאת הכלי. למשל, פנייה מכילה טקסט; החלטת המודל מבקשת lookup_product עם מזהה; תוצאת הכלי מכילה מחיר מהקטלוג. אלה אינם אותו אובייקט. בדיקה של JSON אינה מאמתת את המחיר, והצלחת כלי אינה מוכיחה שהמודל סיכם אותו נכון.

לפני חיבור מודל, כתוב תוצאה צפויה למקרה תקין ולמקרה חסר. לקוח בדיקה מחזיר החלטות קבועות ומאפשר לבדוק את הבקר. אחרי חיבור מודל, שמור גם את תשובותיו ובדוק התאמה לציפייה. אל תחליף בין שני סוגי הראיות.

תוצר בסיס טוב כולל README עם הוראות הרצה, תלות בגרסאות, דוגמאות בדיקה ומגבלות. אל תבנה מערכת שלמה כדי ללמוד תנאי אחד; בנה את החלק שהיחידה מבקשת, הסבר אותו והוכח שהוא עובד.

חקור החלטה אחת לעומק: מה היית משנה אם כמות הנתונים גדלה פי עשרה, אם מקור אינו זמין או אם אדם אחר מקבל אחריות על התהליך? כתוב שתי חלופות, הנחה לכל חלופה וניסוי שיכול להכריע ביניהן. מספרים שבחרת לתרגיל הם הנחות, לא הבטחה לתוצאות אצל לקוח.

קרא את המקור המקושר וחפש את המנגנון הנוגע להחלטה שלך. רשום מועד קריאה, גרסת תוכנה והבדלים בין התיעוד לבין מה שהרצת. בתרגיל המבוסס על ספק, בדוק בחשבון שלך את זמינות המודל או התכונה ואת מגבלות מסלול החשבון.

## Failure Lab

**הכשל שיש להזריק:** הסר מהקלט עובדה חיונית ובדוק אם המודל מודה בחסר.

שמור עותק תקין, ואז צור מקרה נכשל אחד. רשום קלט, ציפייה, תוצאה והודעת שגיאה. אתר את הרכיב הראשון שבו התוצאה סטתה מהציפייה; שינוי הפרומפט אינו תיקון אוטומטי לבעיה בהרשאה, ברשת או בנתונים.

תקן את הגורם, הרץ שוב את המקרה הנכשל ובדוק גם את המסלול התקין. הוסף את המקרה לבדיקות הרגרסיה. הצג ראיה שהתיקון עובד, ולא רק הסבר שהוא אמור לעבוד.

## Challenge

השווה שני אורכי הקשר על אותן שאלות.

בצע את האתגר בלי להעתיק את המימוש הקודם. מותר להשתמש בתיעוד הרשמי. הגש את התוצר יחד עם נימוק להחלטה אחת וגבול אחד של הפתרון. פרויקט מסכם מוגש ללא פתרון מלא, כדי שתוכל להוכיח עבודה עצמאית.

## Mastery Check

הכן שלוש ראיות נפרדות למחוון שמתחת לשיעור:

- **בנייה:** הרץ אותה משימת סיכום עם מסמך קצר, מסמך ארוך והקשר חסר. שמור את הקלט, הפלט, מספר הטוקנים שנצרכו וזמן התגובה. צרף תוצר, קלט ופלט או טבלת החלטות שאפשר לבדוק.
- **אבחון:** הסר מהקלט עובדה חיונית ובדוק אם המודל מודה בחסר. צרף מה קרה לפני התיקון ומה השתנה אחריו.
- **העברה למצב חדש:** השווה שני אורכי הקשר על אותן שאלות. הסבר מדוע הפתרון מתאים ומה עדיין אינו פותר.

שאל את עצמך: האם אני יכול להסביר כל רכיב? האם הבדיקה עשויה להיכשל גם כשהפלט נראה יפה? האם קורא אחר יכול לבדוק את הטענה? סימון בנייה ושמירת ראיות מתעדים עבודה; הם אינם ציון מקצועי ואינם מעניקים שליטה אוטומטית.
