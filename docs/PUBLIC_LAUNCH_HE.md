# פתיחת הקורס להרשמה ציבורית

## מה כבר קיים

ההרשמה והכניסה מבוססות Better Auth. בקשות לנתוני למידה מזוהות לפי המשתמש המחובר בשרת; המשתמש אינו יכול לבחור מזהה של חשבון אחר. ההתקדמות, ההערות, מיקום הקריאה, הטיוטות וההגשות נשמרים במסד הנתונים. סימון קריאת שקופית הוא עזר זמני בדפדפן, ואפשר לבטלו; הוא אינו השלמת תרגיל ואינו מעניק XP.

## מה נדרש לפני שאנשים ייכנסו

1. חשבון אחסון שמריץ Node.js ומספק דיסק קבוע. המסד הנוכחי הוא SQLite; אין לפרוס אותו בדיסק זמני של פונקציה ללא שרת. שמרו גם את תיקיות הביקורת, השאלות ו־Volt על אחסון קבוע לפי `DEPLOYMENT.md`.
2. כתובת ציבורית עם HTTPS. אפשר להתחיל בכתובת שמספק האחסון; דומיין אישי ניתן לחבר בהמשך.
3. שירות SMTP לשליחת אימות כתובת ואיפוס סיסמה, עם כתובת שולח מאומתת. אין צורך למסור סיסמאות בצ'אט: מגדירים אותן במנהל הסודות של האחסון.
4. הגדרות שרת: `BETTER_AUTH_URL`, מפתח אקראי קבוע `BETTER_AUTH_SECRET`, הגדרות SMTP, `MAIL_FROM`, `ADMIN_EMAILS`, `LEGAL_OPERATOR` ו־`LEGAL_CONTACT_EMAIL`. כתובת המנהל שנבחרה היא `oroofarm@gmail.com`; היא אינה משמשת אוטומטית כתובת שולח מאומתת.
5. גיבוי עקבי של המסד והתיקיות הקבועות, ותהליך שחזור שנבדק. שינוי שרת לא צריך ליצור מסד חדש ולמחוק בפועל את ההתקדמות הקודמת.
6. בדיקות ושחרור: `npm ci`, `npm run deploy:check`, מיגרציות תוספתיות לאחר גיבוי, `npm run verify`, והפעלת תהליך האתר מאחורי HTTPS. הגדירו הגבלות גוף בקשה וקצב בקשות ותצורת כתובת לקוח אמינה לפי מדריך הפריסה.
7. בדיקת קבלה באתר הציבורי עם שני חשבונות ניסוי: הרשמה, קבלת מייל ואימות בפועל, כניסה, שמירת עבודה, יציאה וכניסה חוזרת, בידוד נתונים בין חשבונות, ואיפוס סיסמה. בדקו גם שהנתונים נשמרים לאחר הפעלה מחדש של השרת.

## מצב בדיקת ההגדרות — 2026-10-04

`npm run deploy:check` נכשל כי לא הוגדרו `BETTER_AUTH_URL`, `BETTER_AUTH_SECRET`, `MAIL_FROM`, `LEGAL_OPERATOR`, `LEGAL_CONTACT_EMAIL`. הבדיקה נעצרה לפני בדיקת SMTP; אין להסיק מכך שמיילים מחוברים. לא הוקם שרת ציבורי ולא נבדקה שליחת מייל חיה במסגרת הפעולה הזאת.
